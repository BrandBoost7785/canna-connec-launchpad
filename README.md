## Repository setup

> Repository setup. The foundation (database, authorization, authentication primitives, first-run setup) is documented in [docs/FOUNDATION.md](docs/FOUNDATION.md) and [docs/SECURITY_NOTES.md](docs/SECURITY_NOTES.md).

**Requirements:** [Bun](https://bun.sh) (the repo uses `bun.lock`; CI pins Bun 1.4.2) and Node.js 22+.

```sh
bun install --frozen-lockfile
cp .env.example .env   # then fill in values from YOUR OWN development Supabase project
bun run dev
```

### Environment files

- Real `.env*` files are git-ignored. Only `.env.example` (variable names, no values) is tracked.
- Never commit secrets. `SUPABASE_SERVICE_ROLE_KEY` and `LOVABLE_CRON_SECRET*` are server-only secrets.
- Do not use production credentials in development/staging, and do not use development data in production.

### Scripts

| Command                | Purpose                                  |
| ---------------------- | ---------------------------------------- |
| `bun run typecheck`    | `tsc --noEmit`                           |
| `bun run lint`         | ESLint (includes Prettier rules)         |
| `bun run format:check` | Prettier check (`bun run format` to fix) |
| `bun run test`         | Vitest unit tests (no database)          |
| `bun run test:db`      | Database tests on a real PostgreSQL 17   |
| `bun run test:all`     | Unit + database tests                    |
| `bun run test:watch`   | Vitest in watch mode                     |
| `bun run build`        | Production build                         |

### Tests

Vitest is configured in `vitest.config.ts` with two projects:

- `unit` (`bun run test`): no database, no network, no secrets.
- `db` (`bun run test:db`): starts a throw-away **real PostgreSQL 17** server (`embedded-postgres` binaries, must run as a
  non-root user), applies every migration and tests schema, constraints, RLS, `SECURITY DEFINER` functions, audit, business day,
  commission periods and the server-side login/setup flows. No existing database is touched. Details and limitations:
  [docs/FOUNDATION.md](docs/FOUNDATION.md#testing).

### Database migrations

SQL migrations live in `supabase/migrations/` (Supabase CLI convention, `<timestamp>_<name>.sql`) and are described in
[docs/FOUNDATION.md](docs/FOUNDATION.md#migrations). Apply them to a development project first. Migrations must never contain
production seed data.

### Generated files

`src/integrations/supabase/*` and `src/routeTree.gen.ts` are generated by Lovable / TanStack Router. They are excluded
from ESLint and Prettier and should not be edited by hand.

### CI

`.github/workflows/ci.yml` runs typecheck, lint, format check, unit tests and build on pushes and pull requests.
It needs no secrets.
